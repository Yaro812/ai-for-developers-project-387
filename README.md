## Сценарий

Сценарий повторяет базовый путь Cal.com. Там владелец создаёт тип встречи в разделе «Ссылки», гость записывается на публичной странице (календарь, свободные слоты, форма с именем и email), а бронирование появляется у владельца в разделе «Бронирования → Предстоящие». Регистрация, внешние календари и уведомления Cal.com в проект не переносятся.

1. Владелец создаёт тип встречи и указывает название, описание и длительность.
2. Гость открывает приложение без регистрации и выбирает тип встречи.
3. Гость выбирает день в окне бронирования (ближайшие 14 дней), и приложение показывает свободные слоты этого дня; каждый слот длится столько же, сколько выбранный тип встречи.
4. Гость выбирает свободный слот и подтверждает бронирование; приложение сохраняет бронирование, и слоты, которые с ним пересекаются, перестают быть свободными для всех типов встреч.
5. Владелец открывает предстоящие бронирования и видит новое бронирование среди бронирований всех типов встреч.

## Требования

### Правила бронирования

- Окно бронирования занимает 14 календарных дней и сдвигается с течением времени.
- Бронирования не могут пересекаться, даже если у них разные типы встреч; частичное наложение интервалов тоже запрещено, в том числе для двух одновременных запросов.
- Следующее бронирование может начинаться в момент окончания предыдущего.
- Начало окна бронирования (сегодня или завтра), часы работы владельца, часовой пояс, шаг между началами слотов и данные, которые гость указывает при бронировании, фиксируются в спецификации.

### Ограничения

- В приложении нет авторизации и личных кабинетов: владелец один и задан заранее.
- В приложении нет интеграций с внешними календарями.
- Приложение собирается в Docker-образ и запускается в контейнере.
- Данные можно хранить в памяти процесса или в базе; сохранение после перезапуска не входит в приёмку. Если данные хранятся в памяти, README должен предупреждать, что перезапуск сбрасывает бронирования.

### API

- Обязательны TypeSpec-контракт, сгенерированная из него OpenAPI-спецификация и клиентский SDK для фронтенда, сгенерированный из OpenAPI. До выбора стека нужно проверить, что для языка фронтенда есть такой генератор.
- Серверные типы и маршруты генерируются, если фреймворк это поддерживает; иначе бэкенд реализуется по контракту и проверяется тестами.

## Стек

- Бекенд: TypeScript, Node.js 26, Fastify.
- Фронтенд: TypeScript, Vite, React, React Router, Mantine.
- Тесты: Vitest, во фронтенде с Testing Library и jsdom.
- Проверки: oxlint, oxfmt, jactionlint и Git-хуки через hk.
- Окружение: mise фиксирует версии инструментов, задаёт задачи и фоновые серверы.

Цепочка контракта проверена на этих версиях: TypeSpec 1.18 генерирует OpenAPI, а `@hey-api/openapi-ts` 0.99 генерирует из него клиентский SDK на TypeScript.

## Установка

Нужен [mise](https://mise.jdx.dev/getting-started.html). Он ставит Node.js и остальные инструменты, npm-зависимости, Git-хуки и Chromium для браузерного сценария.

```bash
git clone https://github.com/Yaro812/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
```

## Использование

Запустить бекенд и фронтенд в фоне и узнать их адреса:

```bash
mise daemons start
mise daemons urls
```

В основной копии репозитория бекенд отвечает на http://localhost:3000/api/health, а фронтенд открывается на http://localhost:5173 и проксирует `/api` на бекенд.

Остановить серверы:

```bash
mise daemons stop
```

Запустить все проверки (линтеры, сверку OpenAPI с TypeSpec, типы, тесты, браузерный сценарий); GitHub Actions запускает ту же команду на каждый push:

```bash
mise run check
```

Запустить только браузерный сценарий: Playwright собирает фронтенд и поднимает свежий сервер на свободном порту, владелец создаёт тип встречи, гость бронирует слот, владелец видит бронирование:

```bash
mise run e2e
```

Остальные задачи показывает `mise tasks`.

## Запуск в Docker

Образ собирается из исходников, mise для него не нужен. Собрать образ и запустить приложение одним контейнером:

```bash
docker build -t calendar .
docker run -p 3000:3000 calendar
```

Приложение открывается на http://localhost:3000, проверка здоровья отвечает на http://localhost:3000/api/health. Порт внутри контейнера задаёт переменная `PORT`, по умолчанию 3000.

> [!WARNING]
> Типы встреч и бронирования хранятся в памяти процесса ([ADR-0003](docs/adr/0003-in-memory-storage.md)). Перезапуск контейнера стирает их все.

## Деплой

Приложение опубликовано на [Railway](https://railway.com) из первого проекта: https://calendar-production-d15e6838.up.railway.app. Railway собирает образ по `Dockerfile` из исходников и задаёт контейнеру переменную `PORT`, а сервер слушает этот порт.

Выкат проводит агент через [MCP-сервер Railway](https://docs.railway.com/ai/mcp-server). Его подключение описано в `.mcp.json`: агент запускает локальный сервер `railway mcp local` из Railway CLI, версию которого фиксирует `mise.toml`. Секретов в репозитории нет: сервер работает от имени пользователя, вошедшего в CLI.

1. Установить инструменты: `mise install`.
2. Войти в Railway: `mise exec -- railway login`. Вход идёт по OAuth в браузере, сессию CLI хранит в `~/.railway`, вне репозитория.
3. Запустить агента в каталоге проекта. При первом запуске Claude Code спрашивает, доверять ли серверу `railway` из `.mcp.json`. После согласия команда `/mcp` показывает сервер подключённым.
4. Попросить агента выкатить приложение: инструмент `deploy` загружает каталог проекта в сервис `calendar` проекта `calendar`, а `get_logs` и `environment_status` показывают сборку и состояние сервиса.

> [!WARNING]
> Данные живут в памяти контейнера, поэтому каждый выкат и каждый перезапуск сервиса на Railway стирают типы встреч и бронирования.

## Агент в GitHub

Агент [OpenCode](https://opencode.ai/docs/github/) работает в GitHub Actions и отвечает от имени приложения [opencode-agent](https://github.com/apps/opencode-agent), установленного на репозиторий.

### Воркфлоу `opencode`

Файл: [.github/workflows/opencode.yml](.github/workflows/opencode.yml).

- **Назначение.** Агент выполняет команду из комментария: объясняет issue, запускает скилл, правит код и открывает pull request.
- **Событие.** Новый комментарий в issue или pull request (`issue_comment`) и новый комментарий к строке diff (`pull_request_review_comment`), оба с `types: [created]`: правка комментария агента не вызывает.
- **Команды.** `mentions: /opencode,/oc`, набор OpenCode по умолчанию. Пример: `/oc explain this issue`. Скилл вызывается текстом: `/oc запусти скилл to-spec по обсуждению этого issue`.
- **Кто может вызвать.** Владелец, участник организации или коллаборатор репозитория. Комментарии ботов, в том числе самого агента, и посторонних авторов задание пропускает. Pull request из форка задание отклоняет первым шагом, до checkout, поэтому код форка не выполняется рядом с ключом модели.
- **Модель.** `opencode/big-pickle`: бесплатная модель провайдера OpenCode, ей не нужны ни кредиты, ни подписка. Платные модели того же провайдера, например `opencode/deepseek-v4.1-flash`, требуют кредитов в workspace ключа. Ключ лежит в секрете репозитория `OPENCODE_API_KEY` (Settings → Secrets and variables → Actions).
- **Публикация сессий.** `share: false`: сессии агента не публикуются. Репозиторий открытый, а сессия содержит контекст задачи.
- **Права.** Стандартная авторизация OpenCode: `contents: read`, `id-token: write` и `persist-credentials: false` у checkout; комментарии, push и pull request агент делает правами приложения. Токен приложения не доходит до `gh` в оболочке агента, поэтому `gh` получает токен задания с `issues: write`: скиллы читают и публикуют issues так, как описано в [docs/agents/issue-tracker.md](docs/agents/issue-tracker.md). `pull-requests: read` нужен проверке форка.
- **Окружение раннера.** Те же инструменты и зависимости, что локально (`mise install`), поэтому агенту доступна `mise run check`. Скиллы первого проекта (`to-spec`, `to-tickets`, `implement-spec` и остальные из [mattpocock/skills](https://github.com/mattpocock/skills) v1.3.1) ставятся на раннер при каждом запуске; `AGENTS.md` и `docs/agents/` приходят вместе с кодом.
- **Ограничения.** `timeout-minutes: 30`; `concurrency` допускает один запуск на issue или pull request, следующая команда ждёт завершения предыдущей.
- **Результаты.** Ответ агента появляется комментарием в том же issue или pull request, правки — коммитами в ветке pull request. Прогоны и их журналы: [Actions → opencode](https://github.com/Yaro812/ai-for-developers-project-387/actions/workflows/opencode.yml).

### Воркфлоу `triage`

Файл: [.github/workflows/triage.yml](.github/workflows/triage.yml).

- **Назначение.** Предварительный разбор нового обращения по скиллу `triage`: агент проверяет, что приложение уже умеет, называет категорию и следующий шаг, а при нехватке данных задаёт вопросы. Код он не меняет, спецификацию и тикеты не создаёт.
- **Событие.** Новое issue (`issues` с `types: [opened]`). У события нет комментария с командой, поэтому инструкция агенту записана в `prompt` воркфлоу.
- **Кто может вызвать.** Автор issue — владелец, участник организации или коллаборатор. Issues ботов и посторонних авторов задание пропускает.
- **Что пропускается.** Issue с меткой `ready-for-agent`, `ready-for-human`, `wontfix` или `wayfinder:*`: по нему решение уже принято. Скиллы `to-spec` и `to-tickets` публикуют спецификацию и тикеты с меткой `ready-for-agent`, поэтому повторно они не разбираются. Метки описаны в [docs/agents/triage-labels.md](docs/agents/triage-labels.md).
- **Модель и права.** Та же модель и тот же секрет `OPENCODE_API_KEY`, что у `opencode`. `contents: read`, `id-token: write` и `persist-credentials: false` у checkout; `issues: write` нужен `gh` в оболочке агента, чтобы читать issue и ставить метки.
- **Окружение раннера.** Только код репозитория и скиллы: `mise install` не выполняется, потому что разбор ничего не запускает.
- **Ограничения.** `timeout-minutes: 15`; `concurrency` допускает один разбор на весь репозиторий. В очереди GitHub держит один ожидающий запуск: если за время разбора открыть два issue, первое из них останется без разбора — вызовите его комментарием `/oc`.
- **Результаты.** Комментарий агента в issue с пометкой `This was generated by AI during triage` и метки: категория (`bug` или `enhancement`) и состояние (`needs-info` с вопросами или `needs-triage` с предложением следующего шага). Метки `ready-for-agent`, `ready-for-human` и `wontfix` ставит человек. Прогоны: [Actions → triage](https://github.com/Yaro812/ai-for-developers-project-387/actions/workflows/triage.yml).

### От обращения к реализации

1. Пользователь описывает потребность в issue; `triage` оставляет предварительный разбор и вопросы.
2. Владелец отвечает в issue и при необходимости зовёт агента: `/oc разбери обращение по скиллу triage, код пока не меняй`.
3. Когда поведение согласовано, агент запускает `to-spec`, затем `to-tickets`: спецификация и тикеты с зависимостями появляются в GitHub Issues и ссылаются на исходное обращение.
4. Владелец читает спецификацию и тикеты и подтверждает объём комментарием в исходном issue. Ссылку на этот комментарий агент передаёт в pull request реализации.
5. `implement-spec` читает спецификацию и тикеты по ссылкам.

Остановить агента: Cancel workflow на странице прогона прерывает текущий запуск, Disable workflow в меню воркфлоу отключает будущие.
